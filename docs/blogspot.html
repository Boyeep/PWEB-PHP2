Membuat Login Multi-Peran dan CRUD Akun PPDB dengan PHP

Saya membuat RuangAkses, portal simulasi PPDB SMK Nusantara dengan PHP, PDO, dan Bootstrap 5. Satu formulir login melayani Admin, Panitia, Verifikator, dan Siswa. Setelah masuk, setiap pengguna diarahkan ke dasbor yang sesuai dengan peran akunnya.

Coba demo RuangAkses · Lihat kode di GitHub

1. Menetapkan hak akses

Saya mulai dari tindakan yang dibutuhkan setiap peran. Keputusan ini menentukan menu, tujuan setelah login, dan pemeriksaan izin pada setiap rute.

Pembagian peran pada RuangAkses
PeranHak akses
AdminMengelola akun, melihat aktivitas akun, serta membuka data dan dokumen pendaftaran.
PanitiaMemantau calon siswa dan status pendaftaran. Detail yang ditampilkan terbatas pada kebutuhan pemantauan.
VerifikatorMembuka antrean, mengunduh dokumen, dan menyimpan keputusan pemeriksaan.
SiswaMengisi pendaftaran sendiri, membaca hasil, dan memperbaiki berkas saat diminta.

2. Menyusun tabel akun dan pendaftaran

Tabel users menyimpan nama, email unik, hash kata sandi, peran, dan versi autentikasi. Tabel siswa menyimpan NISN serta nomor telepon. Tabel pendaftaran menyimpan pilihan jurusan, dokumen, status, dan catatan. Ketiganya terhubung melalui ID akun. Foreign key dengan ON DELETE RESTRICT melindungi akun dengan riwayat pendaftaran.

Dua tabel lain menyimpan sesi dan aktivitas. app_sessions menggunakan hash ID sesi sebagai kunci, sedangkan activity_logs mencatat tindakan administratif. Schema MySQL dan SQLite tersedia di direktori database.

3. Melakukan login dan memeriksa peran

PHP mencari email menggunakan prepared statement PDO lalu memeriksa kata sandi dengan password_verify(). Setelah verifikasi berhasil, PHP membuat ulang ID sesi dan mencatat ID akun serta versi autentikasi. Peran dibaca kembali dari database pada setiap permintaan. Perubahan email, kata sandi, atau peran menaikkan versi autentikasi agar sesi lama kehilangan akses.

requireRole($actor, 'admin');
return userPage($db, $path, $post, $actor);

Pemeriksaan ini dijalankan di server sebelum halaman pengguna diproses. Pengguna tanpa sesi diarahkan ke halaman masuk. Pengguna dengan sesi dan peran yang tidak sesuai mendapat HTTP 403. Halaman siswa juga memeriksa kepemilikan pendaftaran sebelum menampilkan data atau mengizinkan unduhan.

4. Membuat daftar, pencarian, dan formulir akun

Admin dapat mencari dengan nama, email, atau ID, lalu menggabungkan pencarian dengan filter peran. Halaman daftar menampilkan paling banyak 12 akun per halaman. Input pencarian dan peran dikirim sebagai parameter terpisah dari SQL. Nilai yang berasal dari pengguna di-escape saat ditampilkan di HTML.

Formulir tambah memeriksa nama, keunikan email, pilihan peran, dan panjang kata sandi. Saat mengedit akun, kolom kata sandi boleh dikosongkan untuk mempertahankan hash lama. Kata sandi baru diproses dengan password_hash() sebelum masuk ke database.

Penghapusan memerlukan konfirmasi, permintaan POST, dan token CSRF. Sistem melindungi akun yang sedang dipakai, Admin terakhir, dan akun dengan pendaftaran. Pengecekan hak akses, relasi, dan perubahan data berlangsung dalam transaksi. Token CSRF juga digunakan pada login, logout, dan pengiriman formulir lain.

5. Menghubungkan akun dengan proses PPDB

Siswa mengisi NISN dan nomor telepon, memilih jurusan, serta mengunggah dokumen PDF, JPG, atau PNG hingga 1 MB. PHP memeriksa tipe berkas dan menyimpan isinya bersama pendaftaran. Aplikasi menyajikan dokumen sebagai unduhan setelah memeriksa izin pada server.

Panitia dapat memantau antrean berdasarkan status. Verifikator dapat menetapkan status Terverifikasi atau Perlu revisi. Jika diperlukan revisi, siswa membaca catatan dan mengirim dokumen pengganti. Pendaftaran kemudian kembali ke antrean untuk diperiksa.

6. Menjalankan dan menguji aplikasi

Demo lokal dapat dijalankan dengan php -S localhost:8000 -t public. SQLite membuat data contoh secara otomatis. Untuk MySQL atau MariaDB, impor database/mysql.sql, isi konfigurasi dari .env.example, lalu buat akun Admin melalui skrip CLI.

Demo Vercel memakai SQLite dengan snapshot privat di Vercel Blob. Cookie ruang demo memungkinkan perubahan bertahan ketika pengguna keluar lalu beralih peran di browser yang sama. Cookie autentikasi terpisah. Penulisan snapshot memakai ETag untuk mencegah dua perubahan bersamaan menimpa satu sama lain. Ruang demo berlaku hingga tujuh hari dan dapat dicoba dengan data fiktif.

Pengujian mencakup login empat peran, CRUD, pencarian, pembatasan akses, unggah ulang dokumen, dan keluar akun. Sebanyak 62 pemeriksaan HTTP lulus di SQLite lokal, 58 di MariaDB, dan 63 di demo publik. Tampilan juga diperiksa dengan Chrome pada tiga lebar layar.
